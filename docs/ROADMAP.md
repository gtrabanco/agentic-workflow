# Roadmap

The workflow's **single location index**, in one document: `## Features` orders
the feature units (feature **numbering, ordering, and dependencies**), `## Fixes`
carries the active fixes, and the sections below the tables are the status
machine and the conventions both tables follow. One index, one writer — the same
"single surface, single owner" rule the repo applies to unit docs.

Every feature folder under `docs/features/<NN>-<slug>/` must have a row in
`## Features`, and every row must have a folder (or be explicitly marked
`scheduled`, or `carried by fix #N` when the unit ran through the fix lane —
its carrier is then `docs/fix/<issue-number>-<topic>/`, never a feature
folder). Every fix folder under `docs/fix/<issue-number>-<topic>/` is
registered in `## Fixes` while its work is open.

The two tables are **machine-synced** (fix #507): `bun scripts/docs-generate.mjs`
appends a row for every feature folder missing one, applies a unit doc's
`roadmap_summary:` over its row's summary cell, and never rewrites a hand row —
status, depends-on, summaries and every `idea`/`declined`/`carried by` row stay
owner-written, and fix rows stay owner-managed end to end (the lifecycle below
removes them post-merge).

## Status legend

The pipeline's single ground-truth state machine — every sensor and executor
reads this column, not a SPEC-local marker:

```
idea ──/unit-lane "<idea>" / --from-issue──▶ defined
        (unit doc created; catalog triage recorded in its Evidence)
                                                     │
                     /unit-lane <slug> (plan step)   │
             (engineering half + Tasks P1…Pn)        ▼
                                                   planned
                                                     │
                     execute-phase P1                │
              (branch open; row → in-progress)       ▼
                                                 in-progress
                                                     │
                        PR-open step                 │
              (row → done; merge state in forge)     ▼
                                                    done
```

- `idea` — a roadmap row exists (the wishlist); no unit doc yet.
  **No new file** — a thin row *is* the idea. Next action:
  `/unit-lane "<idea>"` (or `/unit-lane --from-issue <n>` for a tracked issue).
  Set by whoever adds the row.
- `defined` — the unit doc (`docs/features/<NN>-<slug>/SPEC.md`) exists with its
  product half; the catalog steps have not all been planned. Next action:
  `/unit-lane <slug>` (or `/unit-lane --fix <n>` for a fix). Set by `unit-lane`.
- `planned` — the unit doc carries `Tasks P1…Pn` and the triage block. Next
  action: `/execute-phase <NN>` (the lane may run the steps itself). Set by
  `unit-lane`'s `plan` step.
- `in-progress` — branch open, steps executing. Set by `/unit-lane` or
  `execute-phase` P1.
- `done` — built and its PR open (the last step opened the PR); **merge state
  lives in the forge**, not the status — a `done` row may still be awaiting a
  human merge. Set by the PR-open step.
- `declined` — **not a pipeline state.** The feature will never be implemented
  as a separate unit; the row is kept as logical deletion for numbering history
  and traceability (numbers are never reused). Sensors and skills must treat it
  as non-actionable: never a design candidate, never mapped to `idea`, never a
  dependency gate. Set only by an explicit product-owner decision, with the
  reason stated in the row.

Each transition is owned by exactly one skill (a write) — no status is ever
inferred, and no second skill writes the same edge.

## Conventions

- **Feature and fix numbers ARE the forge issue id (owner decision 2026-11-07).** One
  truth: a row's number, its unit folder (`docs/features/<issue-id>-<slug>/` or
  `docs/fix/<issue-id>-<topic>/`), its branch and every receipt carry the GitHub
  issue id — there is never a second, sequential numbering living beside the
  forge. Historical rows keep the old in-order numbers (01–115 plus the
  issue-keyed exceptions) and are never renumbered, re-keyed or reused; every
  **new** feature or fix row takes its number from the GitHub issue that tracks
  it, and a unit with no forge issue yet gets the issue created first.
- A feature that depends on another cannot start until its dependency is **merged**
  (not merely `done` — a `done` dep with an open PR isn't on `main` yet).
- A unit is **executable once the lane's triage has produced its `Tasks`** —
  `planned` (or above) is the gate. `execute-phase`'s dependency gate STOPs and
  redirects a sub-`planned` unit: `idea` → `/unit-lane "<idea>"` (or
  `--from-issue <n>`), `defined` → `/unit-lane <slug>` (or `/unit-lane --fix <n>`).
  The lane's `review` catalog step and `review-change` are the quality gates
  (feature 61 retired the standalone `SPEC-REVIEW-PASS`/`PLAN-REVIEW-PASS`
  pre-execution receipts).
- **Legacy compat:** a pre-U4 roadmap row still reading a plain `planned` with
  no five-state history, whose SPEC's product half is complete, is treated as
  `defined`+`planned` (no redirect) — see `docs/workflow/MIGRATION.md`.
- Keep this table consistent with the feature folders (the `audit-docs` skill
  checks for drift).
- **Fixes** live in `docs/fix/<issue-number>-<topic>/` on branch
  `fix/<issue-number>-<topic>`, with a tracked issue in the project's forge that
  the PR closes via `Closes #<n>` (or the forge's auto-close convention). The row
  is removed from `## Fixes` only **after** the PR merges — do not maintain
  history there.
- `docs/fix/README.md` is a pointer stub: the index it used to hold is the
  `## Fixes` table above, and `docs/fix/_TEMPLATE/SPEC.md` is still the fix SPEC
  format.
