## Goal

Give the workflow a **prompt-injection-safe urgency channel**: an urgent defect
that lands mid-run can consciously interrupt (or defer) the in-flight unit,
without any attacker-controlled text ever being able to trigger the
reprioritization. Urgency is derived **exclusively** from GitHub labels — the one
signal on an issue that a triage+-gated actor must apply and an outsider cannot
forge — never from issue title/body/comment text. `triage-issue` owns and applies
the labels; `workflow-status` reports urgency + the in-flight unit's
interruptibility (never decides); a bounded, tool-less **micro-judge** in the
consumer chooses pause-vs-finish between two paths the label already authorized.

## Product half

Written by `design-feature` from issue #42 (and its 2026-07-11 refinement
comment).

### Context

The workflow has **no injection-safe urgency channel**. When an urgent defect
lands as an issue mid-run, `workflow-status` today treats it like any other
pending fix, and nothing interrupts — or consciously declines to interrupt — the
in-flight unit. The naive fixes are all prompt-injectable: an issue's **title,
body, and comments are attacker-controlled content** (the author or any commenter
writes them), so a skill that reads "URGENT" in text and reprioritizes is
executing an injection with priority.

The design principle that makes this safe: GitHub **labels can only be applied by
users with triage+ permission** on the repo. A label is therefore a
**capability-gated signal** — the one channel on an issue an outsider cannot
forge. Skills must derive urgency **exclusively** from the label object
(`gh issue view N --json labels`), never from title/body/comment text.

The 2026-07-11 refinement (issue #42 comment) resolved the original
"where does the rule table live" question: the pause-vs-finish decision is a
**bounded LLM micro-judge**, injection-safe even though the issue body is
attacker-controlled, because it is (a) tool-less, (b) closed-binary output, (c)
rubric-as-system-prompt (the rule table IS the prompt), (d) fail-safe default
`FINISH_FIRST`. The label already guarantees the fix goes next either way; the
judge only chooses *now* vs. *after this phase*. Its worst-case failure is a
bounded delay between two already-authorized paths — never a dropped fix.

### Business goals

Internal/tooling feature — no external business surface. The outcome served:
the workflow becomes safe to run **unattended** (driver / `ship-roadmap`
`--fullauto`) in a repo that accepts external issues, because an attacker who
files or comments on an issue cannot hijack the run's priorities. It also gives a
human-driven run a principled, auditable answer to "an urgent bug just came in —
do I stop what I'm building?"

### Scope

#### In scope

- **`triage-issue` owns the label vocabulary and applies it.** On a **fix-now**
  verdict with **high severity**, its dated, auditable verdict comment suggests
  **and applies** the correct label, creating it first via `gh label create` if
  the repo lacks it (it runs with the maintainer's forge credentials). Two
  capability-gated labels (see Product decisions):
  - `urgent` — evaluate for interrupt-now (reaches the pause-vs-finish judge).
  - `fix-next` — jump to head of queue, **never** interrupts the in-flight unit
    (bypasses the judge entirely).
  Label application is part of the verdict — **never silent** — and only ever on
  a genuine fix-now/high-severity verdict, never triggered by issue text.
- **`workflow-status` reports urgency, never decides.** Urgent/`fix-next`-labeled
  open issues surface in a dedicated envelope field (`detail.urgent`) derived
  **only** from the labels object, **alongside** the in-flight unit's exact
  interruptibility facts (current phase, dirty tree or clean, distance to the
  next commit boundary — reusing the crash-recovery reconcile it already
  computes). Urgency influences `next.recommended`; the sensor stays "never
  judgment." Trust is **presence-only**: reading the label object is sufficient
  because label application is already triage+-gated.
- **A bounded pause-vs-finish micro-judge** in the **consumer** (driver /
  `ship-roadmap` / human), specified canonically in
  `docs/workflow/ORCHESTRATION.md`:
  1. **Deterministic short-circuit first** — if mechanical facts alone decide, no
     model call: at a commit boundary → interrupt is free, do it; one checkbox
     from phase close → `FINISH_FIRST` automatically. Only the ambiguous middle
     band reaches the judge.
  2. **The judge** — a separate **cheap-tier**, **clean-context**, **tool-less**
     invocation fed the issue content + the interruptibility facts. Closed binary
     output `FINISH_FIRST | INTERRUPT_NOW` + one-line reason, schema-validated
     with the standard repair loop. Rubric-as-system-prompt (the rule table IS
     the prompt, checklist-applied). **Fail-safe default `FINISH_FIRST`** on
     uncertainty, tie, or unparseable output after repair.
- **`ship-roadmap` complies in its SELECT stage** — its existing fix-first
  priority gains the urgent tier: `fix-next` → head of queue; `urgent` → run the
  pause-vs-finish judge against the in-flight unit. `ship-roadmap` **references**
  the one canonical rubric in `ORCHESTRATION.md` — it does not fork a second
  copy.
- **The interrupt path reuses existing infrastructure** — parking a unit is a
  clean voluntary "crash" (WIP commit + progress note); resuming reuses
  `workflow-status`'s `RESUMABLE` verdict + `execute-phase`'s idempotent phase
  re-entry. No new park/resume machinery.
- **`init-workspace` seeds the labels** — at scaffold time it creates the
  `urgent` + `fix-next` labels (name + color convention) in the target repo, and
  its **upgrade mode** adds them to an existing install that pre-dates this
  feature. Additive-only, per the upgrade-mode contract.
- Version/bookkeeping via `bump-skill` across every touched skill
  (`triage-issue`, `workflow-status`, `ship-roadmap`, `init-workspace`) + both
  CHANGELOGs + both README skill tables. `ORCHESTRATION.md` is a doc, not a skill.

#### Out of scope / non-goals

- **Deriving urgency from any text** — title, body, or comments. The body only
  *informs* the judge's choice between the two already-authorized paths; it can
  never escalate beyond what the label grants, and an **unlabeled** issue never
  reprioritizes anything regardless of its text. (Owner: this feature's core
  invariant.)
- **A timeline/actor-permission cross-check** — verifying the labeling actor's
  triage+ permission via `gh api .../timeline`. Presence is already
  capability-gated; the cross-check is explicitly deferred as unneeded
  defense-in-depth. (Owner: a future hardening idea if a demoted-actor threat
  ever materializes — logged in `decisions.md`.)
- **The judge holding any effector** — it is pure classification, tool-less, by
  construction. Giving it tools would reintroduce the injection surface. (Owner:
  none — a hard invariant.)
- **`workflow-status` deciding pause-vs-finish** — it reports facts; the decision
  lives only in the consumer. (Owner: the consumer — driver / `ship-roadmap` /
  human.)
- **New park/resume machinery** — reuse `RESUMABLE` + idempotent re-entry.
  (Owner: features 03 / existing `execute-phase`.)
- **Pinning the judge to a specific model** — the rubric names *cheap-tier,
  clean-context, tool-less*; the exact model id is an Engineering-half decision,
  not a product one. (Owner: `plan-feature`.)
- **A `template/` mirror** — the labels seed into target repos via
  `init-workspace` behavior, not a templated file; `ORCHESTRATION.md` is
  repo-level workflow doc. (Owner: n/a.)
- **CI enforcement** — none; consistent with the repo's "no application build"
  verification model. (Owner: n/a.)

### Product decisions

- **Two labels, not one** (chosen). `urgent` = evaluate for interrupt-now (reaches
  the judge); `fix-next` = head of queue, never interrupts. Rationale: the
  non-interrupting "do this next but don't stop the current phase" priority is a
  genuinely distinct, useful signal, and making it a separate capability-gated
  label keeps it out of the judge entirely (cheaper, and it can never be
  escalated to an interrupt by issue text). The judge's `FINISH_FIRST` still
  exists for the `urgent`-but-not-now outcome.
- **`triage-issue` owns the label vocabulary** (chosen). The label names, colors,
  and application rules are defined in one place — `triage-issue` — and every
  other skill (workflow-status read, ship-roadmap SELECT, init-workspace seed)
  refers to that vocabulary. Rationale: a single writer/definer prevents the two
  labels from drifting into three spellings across skills.
- **Presence-only trust** (chosen). `workflow-status` establishes trust by
  reading the label object; it does **not** cross-check the labeling actor's
  permission via the issue timeline. Rationale: label application is already
  triage+-gated by GitHub, so presence is inherently capability-gated; the
  timeline check is deferred defense-in-depth (logged in `decisions.md`).
- **Include label seeding in this feature** (chosen). `init-workspace` seeds the
  labels at scaffold time and via upgrade mode. Rationale: the convention should
  land in every target project from day one rather than only materializing the
  first time `triage-issue` happens to create it.
- **Rule table lives in the judge's system prompt, canonical in
  `ORCHESTRATION.md`** (resolved by the issue's 2026-07-11 refinement, recorded
  here for traceability). `ship-roadmap` references the same table.

**Data-flow invariant (the security property):** the only path from an issue to a
priority change is `label object → sensor field → consumer judge`. Issue
title/body/comment text may *inform* the judge's choice between the two paths the
label already authorized, but can never create urgency where no label exists.

### Design

**1 — Label vocabulary (`triage-issue`, P1).** On a **fix-now + high-severity**
verdict only, the dated verdict comment states which label it applies and applies
it: `gh label create <name> --color <hex> --description <text>` if the repo lacks
it, then `gh issue edit <N> --add-label <name>`. `urgent` = reaches the judge;
`fix-next` = head of queue, never interrupts. Never triggered by issue text; never
silent.

**2 — Sensor field (`workflow-status`, P2).** `detail.urgent` lists open issues
carrying either label, read **only** from `gh issue view <N> --json labels` (or
`gh issue list --label <name> --json number,labels`), presence-only, no
title/body/comment parse, no actor timeline check. Alongside it the field carries
the in-flight unit's interruptibility facts — current phase, dirty/clean tree,
distance to the next commit boundary — taken from the crash-recovery reconcile the
sensor already produces. The sensor emits facts; it never emits a pause-vs-finish
decision. Urgency may influence `next.recommended` (a recommendation, not a
decision).

**3 — Pause-vs-finish micro-judge (`ORCHESTRATION.md`, P3).** Canonical rubric:
1. **Deterministic short-circuit (no model call).** At a commit boundary (clean
   tree, phase closed) → interrupt is free → `INTERRUPT_NOW`. One checkbox from
   phase close (dirty, ≤1 task left) → `FINISH_FIRST`. `fix-next` label → never
   reaches the judge (head of queue, no interrupt). Only the ambiguous middle band
   continues.
2. **The judge.** A cheap-tier, clean-context, **tool-less** invocation fed the
   issue content + the interruptibility facts. Output closed-binary
   `FINISH_FIRST | INTERRUPT_NOW` + one-line reason, schema-validated with the
   standard envelope repair loop. The rule table **is** the system prompt
   (rubric-as-system-prompt), checklist-applied. **Fail-safe default
   `FINISH_FIRST`** on uncertainty, tie, or unparseable output after repair.
The label guarantees the fix runs next either way; the judge only chooses *now*
vs. *after this phase* — worst case a bounded delay, never a dropped fix.

**4 — Consumer wiring (`ship-roadmap` SELECT, P3).** SELECT gains the urgent tier:
`fix-next` → head of queue (no interrupt); `urgent` → run the `ORCHESTRATION.md`
judge against the in-flight unit. `ship-roadmap` **references** the one rubric; it
does not restate it.

**5 — Label seeding (`init-workspace`, P4).** Scaffold and upgrade mode create the
two labels (name + color convention) in the target repo, additive-only per the
upgrade-mode contract.

**6 — Interrupt/park path (no new machinery).** Parking is a clean voluntary
"crash" (WIP commit + progress note); resuming reuses `workflow-status`'s
`RESUMABLE` verdict + `execute-phase` idempotent phase re-entry.

### Decisions to confirm

- **Judge model is a *tier*, not a pinned id** (confirmed — resolves the
  product-half deferral). The rubric names *cheapest capable tier in the fleet ·
  clean context · tool-less*; no concrete model id is written, because the
  workflow is model-agnostic across 70+ agents (per the README model-equivalence
  table). Pinning an id would break portability. Recorded in `decisions.md`.
- **Label colors** (confirmed): `urgent` → `#B60205` (red), `fix-next` →
  `#D93F0B` (orange). Convention only; any repo may recolor — the **name** is the
  contract, the color is cosmetic. Recorded in `decisions.md`.
- **Both labels on one issue** (confirmed): `urgent` wins — the issue reaches the
  judge (the interrupt-evaluating path strictly dominates head-of-queue). Stated
  in the sensor + rubric.

### Dev scenarios

**Happy path.** An external issue is filed and a maintainer runs `triage-issue`;
the verdict is fix-now + high severity, so the comment applies `urgent`. Mid-run
`workflow-status` surfaces it in `detail.urgent` with the in-flight facts (P2,
dirty tree, 2 tasks from commit boundary). The consumer's short-circuit sees the
middle band, calls the judge, which returns `FINISH_FIRST` (close to a boundary);
the fix runs immediately after the phase commits.

**Failure / edge modes (implemented + tested in P5 hardening):**
- `urgent:label-exists` — `gh label create` errors because the label already
  exists → treated as success (create-if-missing), then `--add-label` proceeds.
- `urgent:no-permission` — the actor lacks triage+ to create/apply the label →
  `triage-issue` reports the failure in its verdict comment (does not silently
  drop it); the run is unaffected (no urgency asserted without a label).
- `urgent:both-labels` — an issue carries both `urgent` and `fix-next` → `urgent`
  wins (reaches the judge); documented in the sensor + rubric.
- `judge:unparseable` — the judge's output fails schema validation after the
  repair loop → fail-safe `FINISH_FIRST` (never a dropped fix).
- `judge:fix-next` — a `fix-next`-labeled issue never reaches the judge (head of
  queue, no interrupt) — the deterministic short-circuit handles it.
- `status:issue-closed` — the fix ships and the issue closes → it drops from
  `workflow-status`'s open-issue scan automatically; no manual label strip
  required.
- `status:no-labels` — an issue with "URGENT" in its **title/body** but no label
  never appears in `detail.urgent` (the core injection-safety invariant).
