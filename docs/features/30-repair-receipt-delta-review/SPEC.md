## Goal

Make the review→fold loop **decision-driven and delta-scoped**: every fold
batch ends with a structured, greppable REPAIR-RECEIPT that (a) classifies the
batch by whether the fixes were locally decidable or invalidate a plan
assumption, (b) branches the closing `→ Next:` on that classification and the
batch's materiality — re-review required (delta), re-review optional/skipped,
or a replan route —, and (c) hands the reviewer's own reproducer to the fold so
the next review verifies against a materialized check instead of re-deriving
one. The post-fold re-review defaults to **delta mode** (re-verify folded rows
at their cited locations, review only the fold diff), escalates to a full pass
on defined triggers, and stays inside the existing two-cycle cap.

### Context

The review→fold loop already terminates and its pieces have single owners:

- `review-change` reviews the diff, classifies every finding through
  `review-implementation`'s closed class set, persists fix-now rows in the
  unit's `review-findings.md` ledger, and posts a SHA-bound `REVIEW-PASS`
  receipt when clean.
- `fold-findings` repairs fix-now rows (root-cause fix, gate run, one atomic
  commit, per-row `folded: no → yes` flip) and prints a per-finding verdict
  table plus a tally, ending in a fixed `→ Next:` block.
- From cycle 2 on, `review-change` re-verifies every `folded: yes` row at its
  cited location before anything else, and the only legitimate bypass of the
  `file:line`+axis dedupe is a row marked `regression of <id>`.
- The loop is bounded at two review→fold cycles counted from `REVIEW-RAN`
  marks and forge receipts; a third cycle never starts without an explicit
  user instruction.
- Each verified finding gets a durable `finding-mark@1` row whose `recheck`
  cell carries the method + reproducer the reviewer used; each review run
  leaves a `review-mark@1` row.

What is missing, and the problem it causes:

1. **The re-review is full-scope by default.** Nothing tells the reviewer that
   the fold diff is the candidate; a delta-able fold batch pays a second full
   review of the whole unit. On an unattended driver this is the single
   largest avoidable token cost per finding cycle.
2. **The fold's outcome is prose, not a decision.** `fold-findings` prints
   verdicts and a tally, but the orchestrator or human must re-derive whether
   the next step is a delta re-review, a skip, or a replan. The decision is
   repeated per cycle from first principles instead of being emitted once,
   with evidence, by the skill that just did the folding.
3. **The replan signal has no structured route.** `FOLD_POLICY` knows the
   definition of fixed and the forbidden list, but "this finding invalidates a
   plan assumption" has no classification, no freeze behavior, and no receipt
   field — it surfaces only as a per-finding `REPLAN` verdict line.
4. **The reviewer's reproducer dies in the ledger.** `finding-mark@1`'s
   `recheck` cell carries the exact reproducer, but `FOLD_POLICY` never
   materializes it: the fold may add a weaker check, and the next re-review
   re-derives the verification from scratch.
5. **The escalation trigger does not exist.** The roadmap says a delta review
   escalates "when the diff is large or touches shared surfaces", but no
   definition of either exists anywhere in the skills or workflow docs.

Evidence rows E-01…E-20 (below) ground each claim; external research rows
E-11…E-14 ground the classification axis. Feature 29's bounded implementation
discovery (merged) already established the pattern this feature generalizes on
the review side: validate what was frozen against current state, in a bounded,
receipt-shaped act.

### Business goals

- **Token/time economy of unattended delivery.** Plan-heavy, loop-cheap: the
  pipeline's accepted trade (features 08, 22, 28) is to spend tokens deciding
  and verifying *once*, up front, so execution and review run fast. This
  feature removes the loop's largest recurring re-payment: full re-reviews of
  already-scoped fold diffs.
- **Senior-dev convergence behavior.** A senior developer repairs and
  continues when the fix is locally decidable, and stops to re-plan when the
  finding invalidates an assumption of the plan — never looping a
  non-convergent batch. External evidence (Boehm & Basili 2001; Reason's
  active-vs-latent failures; ISO/IEC 14764's intent-based maintenance
  categories; IEEE 1028's review economics) supports exactly this split; see
  evidence rows E-11…E-14 and `decisions.md` D30-1.
- **Same loop invariants, cheaper cycles.** The two-cycle cap, the
  frozen-acceptance check, the receipt-at-head merge gate, and the
  no-reclassification rule all hold unchanged; only the *cost per cycle* and
  the *quality of the handoff* change.

### Scope

#### In scope

- **IS-1 — REPAIR-RECEIPT emission.** After every fold batch (including an
  empty or frozen one), `fold-findings` prints a fixed, greppable receipt
  block carrying: repaired finding ids with their `finding-mark@1` references,
  refuted/open rows, the gate's exit codes at the head it ran on, the batch
  class, and the fold-diff shortstat.
- **IS-2 — Impact-rule batch classification.** The batch class is derived from
  the per-finding classes the reviewer already froze, using the impact rule:
  repair-in-place (fix locally decidable; no new planning decisions) vs
  replan-class (`replan-in-unit` / `decision-required` — the fix invalidates a
  plan assumption or requires decisions the plan never made). The vocabulary
  stays single-owner: `review-implementation`'s closed class set; the receipt
  never invents a parallel docs-vs-code vocabulary.
- **IS-3 — Conditional `→ Next:` branching.** The receipt's closing block
  branches on the batch class and materiality:
  `RE-REVIEW-REQUIRED (delta)` for behavioral or high-severity batches;
  `RE-REVIEW-OPTIONAL` / `RE-REVIEW-SKIPPED` only when every row is
  repair-in-place with report-note materiality (docs-only, no behavioral
  surface). The consumer (orchestrator or human) decides on OPTIONAL/SKIPPED;
  **the default with no decision is re-review**.
- **IS-4 — Freeze-batch rule.** If the batch contains at least one
  replan-class finding, `fold-findings` folds nothing from it: no
  `folded: yes` flips, no commits. The receipt records the replan route plus
  every retained (unfolded) row id; the loop stops and routes to planning.
- **IS-5 — Delta-mode default re-review.** The post-fold re-review in
  `review-change` defaults to delta mode: re-verify every folded row at its
  cited location, review the fold diff only, require the gate green at the
  reviewed head and the sibling `ACCEPTANCE.md` blob recomputed to an exact
  match, then post the normal SHA-bound `REVIEW-PASS`. New findings must be
  genuinely new: same `file:line`+axis re-reports are admitted only as
  `regression of <id>` (or `DISPUTED` with evidence), extending the existing
  cycle-2 rule from folded rows to the whole delta scope.
- **IS-6 — Escalation to a full pass.** Delta mode escalates to a full
  re-review when either trigger holds: (1) *width* — any changed file lies
  outside the union of the `file:line` locations cited by the batch's folded
  findings; (2) *size* — the fold diff exceeds 200 changed lines in total or
  touches more than 15 files. The escalation states which trigger fired and
  the observed numbers.
- **IS-7 — Cap semantics preserved.** Delta re-reviews are review→fold cycles;
  the cap keeps its existing counting source (`review-mark@1` marks + forge
  receipts), unit-level and family-agnostic; `LOOP CAP REACHED` and the
  user-only third cycle are unchanged.
- **IS-8 — Reproducer handoff.** `FOLD_POLICY` consumes `finding-mark@1`'s
  `recheck` cell: the fold materializes that reproducer as the regression
  check and runs it as the fixed evidence — it never invents or re-derives the
  reproducer. A recheck cell that cannot be materialized as a runnable check
  yields `BLOCKED` with the missing input named.
- **IS-9 — Skill bumps and pins.** Minor version bumps to `fold-findings`,
  `review-change`, and `pre-execution-review`; the loop-discipline pins in
  `scripts/review-loop-discipline.test.mjs` are updated to assert the new
  contract and are never weakened.
- **IS-10 — Loop-termination invariant.** A SKIPPED outcome is always
  accompanied by a receipt; no branch of the new logic can start an unbounded
  sequence of delta cycles (the cap covers deltas), and the manual
  `review-change → fold-findings → review-change` path and the programmatic
  outer driver consume the same receipt.

#### Out of scope / non-goals

- **`audit-pr` is unchanged** — it keeps consuming the SHA-bound
  `REVIEW-PASS` receipt at the exact PR head; delta mode is invisible to it
  (a stale receipt is still BLOCKED, routed back to `/review-change`).
- **No schema-package change** — the receipt is a printed fixed block; no
  `@gtrabanco/agentic-workflow-schema` contract, envelope field, or JSON
  Schema is added (owned by: none; untouched).
- **No new durable ledger row type** — `folded` flags, `REOPENED` annotations,
  `finding-mark@1`, and `review-mark@1` keep their existing single owners; the
  receipt adds no row (owned by: `pre-execution-review` LEDGERS map, unchanged).
- **No planning-side loop changes** — the materiality floor, two-cycle cap,
  and wording-only determination for the *spec/plan* loop belong to feature 31
  (`planning-review-materiality`, issue #171).
- **No severity-vocabulary or LEDGERS-prose reconciliation** — belongs to
  feature 32 (`review-consistency-pack`, issue #172).
- **No turn-contract migration** — bespoke contract text reconciliation belongs
  to feature 33 (`turn-contract-single-owner`, issue #173).
- **No automatic issue creation** — an unresolved replan routes to the user /
  orchestrator; `fold-findings` never creates issues (existing rule, restated).
- **No `template/` mirror change** — the receipt is output, not a ledger
  convention the template mirrors.
- **No runtime/provider dependency** — the loop stays portable; no MCP, CI, or
  external tool is required to consume the receipt.

### Product decisions

All recorded with rationale in `decisions.md` (2026-09-07); summary:

- **D30-1 Impact rule** — classify findings by "does the fix require new
  planning decisions / invalidate a plan assumption?", not by artifact type;
  reuses `review-implementation`'s closed class set (user-accepted after two
  research rounds).
- **D30-2 Freeze-batch** — any replan-class finding freezes the whole batch:
  no folds, receipt records route + retained ids (user-selected).
- **D30-3 Receipt is a printed block, not a ledger** — durable state stays in
  the existing ledgers; no schema change.
- **D30-4 Delta default** — skipping re-review requires an all-repair-in-place,
  report-note-materiality batch; unattended default is re-review.
- **D30-5 Escalation triggers** — width (outside cited-file union) or size
  (> 200 lines or > 15 files); must state trigger + observed numbers
